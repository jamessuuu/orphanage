orphanage

Crawls a site the way a crawler does — following links from the root — reads the sitemap separately, and reports where the two disagree: orphans, unlisted pages, broken internal links, redirect chains, deep pages, dead sitemap entries.

See a sample report Source

MIT. Zero runtime dependencies. Node 20+.

Forty findings, and every one was noise

Run against agentjames.vercel.app on 2026-09-05, orphanage crawled the site, read its sitemap, and reported 40 pages the crawl had reached that the sitemap never declared. Every one of those 40 turned out to be noise. Thirty-five were /console?c=... permalinks, each one declaring rel=canonical back to /console — the same page, forty different query strings. The other five were non-HTML endpoints a sitemap of pages was never going to list: things like llms.txt, agent.json, resume.md, and a CV PDF.

Splitting canonical-consolidated URLs and non-HTML resources into their own buckets took the unlisted count from 40 down to 0. With the noise gone, the one finding that actually mattered became visible: /games is declared in the sitemap and is not reachable by following any link from the homepage.

A tool that buries one real finding under forty false ones is worse than no tool. That is not a caveat on this project. It is the reason the canonical and content-type buckets exist at all.

What a report looks like

Every finding category gets its own section, and an empty one says so in plain language instead of just staying quiet:

1 found orphans in the sitemap, unreachable by following links from the root — /games
0 found unlisted every page the crawl reached is declared in the sitemap
0 found broken internal links, redirect chains, deep pages, dead sitemap entries clean

The sample linked above is not that run — it is a small, committed fixture site built to exercise all six finding categories at once, so you can see every section populated without trusting a screenshot.

The honesty rules

  • If the crawl hits its page cap, the report says so, explicitly, next to the orphan and unlisted findings, because a truncated crawl cannot tell a genuine orphan apart from a page it simply had not reached yet.
  • A page excluded by this tool's own robots.txt compliance is shown as excluded, not counted as broken or orphaned. The tool found a link to it; it chose not to follow it.
  • A dead sitemap entry is only reported for a URL whose live status was actually observed. A sitemap URL that was neither crawled nor separately checked is reported as unknown status, never guessed at.

The report fetches nothing

Zero JavaScript, zero network requests, a mobile viewport tag, a print stylesheet, and every collapsible section open by default, because a collapsed <details> disappears entirely from a printed PDF. overflow-wrap: anywhere is set on every URL cell so a long one cannot push the layout wider than a phone screen.

orphanage --check <report.html> enforces all of that mechanically, on any report, including one you did not generate.

Use it

node bin/orphanage.mjs https://example.com/
node bin/orphanage.mjs --check report.html

Exit 0 nothing to report · 1 a finding was produced, or the report failed its own --check, which is the CI signal · 2 used wrongly, so nothing was measured.

What it will not tell you

  • Whether GPTBot, ClaudeBot, or Googlebot specifically can reach a page. This tool crawls once, with one ordinary browser-style User-Agent. A sibling tool, built separately, handles per-crawler access.
  • Anything on a page whose navigation is injected by client-side JavaScript. It sees exactly what a crawler that does not execute JavaScript sees.
  • Whether a page deserves to be indexed. A correctly-orphaned thank-you page still shows up in the orphans list; deciding that is a judgment call for a person, not this tool.
